# Full-text search and faceted discovery

PR 6 introduces provider-neutral search and the first PostgreSQL implementation.

## Search architecture

```text
downstream registry configuration
            ↓
@civic-registry/search
  request/response contract
  validation
  search index text generation
            ↓
SearchProvider
            ↓
PostgresSearchProvider
            ↓
PostgreSQL tsvector + generic JSONB facets
```

The web application and downstream registries depend on the search contract,
not PostgreSQL SQL.

A future OpenSearch or Elasticsearch implementation can satisfy the same
`SearchProvider` interface.

## Searchable data

Only fields configured with:

```yaml
searchable: true
```

are copied into the full-text search index.

The record ID and tags are also indexed.

Enum fields include both their stored value and configured human-readable label
when they are searchable.

Fields that are present but not configured as searchable do not enter
`search_text`.

## PostgreSQL index

Migration `0002_search_index.sql` adds:

- `search_text` — normalized text generated by the engine;
- `search_document` — a stored `tsvector` generated with PostgreSQL's
  `simple` dictionary;
- a GIN index on `search_document`.

New record writes and updates maintain `search_text` automatically.

## Upgrading existing installations

Records created before PR 6 have an empty search index until they are reindexed.

After applying the migration, run:

```bash
pnpm db:reindex
```

To rebuild only one installed registry:

```bash
pnpm db:reindex -- public-document-catalog
```

Reindexing reads the current stored registry configuration, so it respects the
current `searchable` flags.

## Supported search constraints

The generic search request supports:

- full-text query;
- record type;
- one or more statuses;
- one or more tags;
- configured field filters;
- configured numeric/date/date-time ranges;
- relevance sorting;
- updated date sorting;
- publication date sorting;
- configured field sorting;
- pagination.

Configured field filters and field sorting require a selected record type so
the engine can validate the field against one unambiguous schema.

## Facets

Search responses include:

- record-type counts;
- status counts;
- tag counts;
- term facets for configured filterable fields;
- min/max range facets for filterable date, date-time, integer, and decimal
  fields.

Facets are calculated within the current filtered result set.

## Public interface

The reference web application exposes:

```text
/registries/:registryId/search
/registries/:registryId/records?type=:recordTypeId
/api/registries/:registryId/search
```

Search forms use GET parameters. Search and filter states are therefore
bookmarkable and shareable.

The public HTML and JSON endpoints force `visibility: public` regardless of
incoming query parameters.

## Query parameters

Common parameters:

- `q` — full-text query;
- `type` — record type;
- `status` — status value;
- `tag` — tag;
- `sort` — `relevance`, `updated`, `published`, or `field:<fieldId>`;
- `order` — `asc` or `desc`;
- `page`;
- `pageSize`.

Configured term filters use:

```text
f_<fieldId>
```

Configured ranges use:

```text
from_<fieldId>
to_<fieldId>
```

## Deliberate limitations

PR 6 does not attempt fuzzy semantic search, embeddings, typo correction, or a
dedicated external search cluster.

The PostgreSQL provider is intended to provide a robust default with a clean
escape hatch to specialized search infrastructure when scale or ranking needs
justify it.
